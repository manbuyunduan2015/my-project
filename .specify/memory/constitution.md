# my-project Constitution

## Core Principles

### I. 代码质量至上

所有代码必须达到可维护、可读、可测试的标准。非可提交状态视为未完成。

- **编码规范**：遵循项目语言主流风格指南（如 PEP 8、Google Style Guide 等），通过 linting 工具自动化检查，CI 中强制通过方可合并。
- **命名清晰**：变量、函数、类的命名必须准确表达意图，禁止缩写歧义。
- **函数职责单一**：每个函数只做一件事，超过 30 行需考虑拆分。
- **注释原则**：默认不写注释。仅在 WHY 非显而易见时补充简短说明（隐藏约束、特定 bug 的变通方案、反直觉的架构决策）。不注释 WHAT（代码做什么），那是命名该做的事。
- **零技术债务策略**：新代码不引入已知债务。发现债务立即修复或在同一 PR 中处理。

### II. TDD 驱动开发（不可协商）

所有功能与 bug 修复必须遵循 TDD 流程。无测试的代码视为不存在。

- **红-绿-重构循环**：先写失败的测试 → 编写最小实现使测试通过 → 重构消除重复。严格循环，不可跳过。
- **覆盖率门槛**：行覆盖率与分支覆盖率均不低于 **90%**。低于阈值的 PR 自动拦截，不得合并。
- **测试分层**：
  - 单元测试：覆盖核心逻辑、工具函数、纯函数。要求覆盖率 ≥ 95%。
  - 集成测试：覆盖 API 端点、数据库交互、外部服务通信。
  - 端到端测试：覆盖关键用户路径。黄金路径 + 边界场景必须覆盖。
- **测试命名**：描述行为而非实现。格式：`should_期望结果_when_条件` 或 `测试场景描述`。
- **测试独立性**：每个测试用例独立运行，不依赖执行顺序。使用 fixture/mock 隔离外部依赖。
- **Mock 策略**：单元测试使用 mock 隔离，集成测试必须命中真实数据库（禁止 mock 数据库），端到端测试走完整链路。

### III. 用户体验一致性

用户在产品的任何角落都应感受到统一的体验。不一致的 UI 视为 bug。

- **设计系统**：所有 UI 组件必须来自统一的设计系统/组件库。禁止页面中直接编写样式绕过组件。
- **交互一致性**：相同的操作产生相同的反馈。加载态、空状态、错误态、成功态的呈现方式全局统一。
- **文案规范**：错误消息、提示文本、按钮文案遵循统一的语调指南。面向用户的文案不得出现技术术语。
- **可访问性**：满足 WCAG 2.1 AA 级别要求。键盘导航、屏幕阅读器兼容、色彩对比度达标。
- **响应式设计**：所有界面必须在主流断点（手机、平板、桌面）下正确渲染。

### IV. 性能指标约束

性能不是优化项，是需求。用户感知的延迟不可超过 100ms。

- **UI 响应时间**：任何用户交互（点击、输入、滚动）的视觉反馈严格控制在 **100ms 以内**。超过 100ms 的操作必须显示加载指示器。
- **首屏加载**：关键渲染路径优化，FCP（First Contentful Paint）≤ 1.5s，LCP（Largest Contentful Paint）≤ 2.5s。
- **API 响应**：P95 延迟 ≤ 200ms，P99 延迟 ≤ 500ms。慢查询必须被索引或缓存优化。
- **包体积预算**：首次加载 JS 包 ≤ 200KB（gzip），CSS ≤ 50KB（gzip）。超出需走审批。
- **性能监控**：核心指标纳入 CI 性能门禁。回归超过 10% 自动拦截。
- **数据库查询**：单页面请求查询数 ≤ 10 次。N+1 查询视为 bug。

### V. 可观测性与简洁性

系统行为必须可被观察、可被调试。复杂性需要被证明，而非被默认。

- **结构化日志**：所有服务输出结构化日志（JSON 格式），包含 trace ID、时间戳、级别、上下文。禁止裸 print/debug 输出。
- **错误处理**：错误边界清晰，错误信息包含足够上下文用于诊断。禁止吞没异常（silent catch）。
- **YAGNI 原则**：不为假设的未来需求编写代码。三个类似场景出现后再考虑抽象。
- **版本管理**：遵循语义化版本（MAJOR.MINOR.PATCH）。破坏性变更必须升 MAJOR 并附带迁移指南。
- **提交规范**：遵循约定式提交（Conventional Commits），类型 + 范围 + 描述。

## 代码审查规范

所有代码变更必须经过代码审查方可合并。

- **审查要求**：至少一名具有审查权限的协作者批准。作者不可自审自批。
- **审查清单**：代码质量（遵循本宪法原则）、测试覆盖率、性能影响、安全隐患（OWASP Top 10）、命名与注释。
- **小步提交**：单个 PR 变更不超过 400 行（不含自动生成代码）。大功能拆分为可独立审查的小 PR。
- **审查时效**：代码审查应在提交后 24 小时内完成。超时升级通知。
- **自动化先行**：lint、测试、类型检查由 CI 自动执行。人工审查专注于逻辑正确性和架构合理性。

## 质量门禁

代码合并前必须通过以下门禁，任何一项失败即拦截。

| 门禁项 | 阈值 | 工具 |
|--------|------|------|
| Lint 检查 | 0 错误，0 警告 | ESLint / Pylint / 等效工具 |
| 类型检查 | 0 错误 | TypeScript / mypy / 等效工具 |
| 单元测试覆盖率 | ≥ 90% 行覆盖率，≥ 90% 分支覆盖率 | Jest / pytest-cov / 等效工具 |
| 集成测试 | 全部通过 | 项目测试框架 |
| 端到端测试 | 黄金路径全部通过 | Playwright / Cypress / 等效工具 |
| 性能回归 | 核心指标变化 ≤ 10% | Lighthouse CI / 自定义基准 |
| 安全扫描 | 0 高危漏洞 | SAST / 依赖审计 |

## Governance

本宪法为项目最高开发准则，凌驾于所有其他实践之上。

- **修订流程**：宪法修订需提交 Pull Request，说明修订理由、影响范围、迁移计划。至少两名核心贡献者批准方可合并。
- **版本策略**：遵循语义化版本。MAJOR 为不兼容的治理变更，MINOR 为新增原则或章节，PATCH 为措辞澄清和排版修正。
- **合规审查**：每个 PR/合并请求必须验证是否符合宪法原则。代码审查者有责任指出违规行为。
- **复杂度证明**：引入复杂性的代码必须在注释或 PR 描述中证明其必要性。简洁为默认选择。
