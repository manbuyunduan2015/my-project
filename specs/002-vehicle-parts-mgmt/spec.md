# Feature Specification: 整车零部件管理系统（Vehicle Parts Management System）

**Feature Branch**: `002-vehicle-parts-mgmt`  
**Created**: 2026-04-26  
**Status**: Draft  
**Input**: User description: 企业内部后台管理系统，实现整车信息、零部件信息、整车零部件装配关联关系及用户权限管理的统一维护

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 管理员登录与首页概览（Priority: P1）

系统管理员使用用户名和密码登录系统，进入首页后一眼看到核心统计数据：整车总数、零部件总数、用户总数、库存预警数量，以及各类可视化图表。

**Why this priority**: 登录是系统入口，首页是用户日常操作的第一屏，没有它们系统不可用。

**Independent Test**: 用户使用有效凭据登录成功后，能看到首页统计数据卡片和图表，数据与数据库中实际记录一致。

**Acceptance Scenarios**:

1. **Given** 用户已注册且状态为启用，**When** 输入正确用户名和密码并提交，**Then** 登录成功，跳转至首页，返回有效 Token
2. **Given** 用户输入错误密码，**When** 提交登录，**Then** 提示"用户名或密码错误"，不跳转
3. **Given** 用户已登录且 Token 有效，**When** 访问首页，**Then** 展示四项统计卡片、零部件类别柱状图、库存预警图表、最近新增列表
4. **Given** 用户 Token 已过期，**When** 访问任何受保护页面，**Then** 自动跳转登录页
5. **Given** 用户点击退出，**When** 确认退出，**Then** 清除本地 Token，跳转登录页

---

### User Story 2 - 用户管理（Priority: P1）

超级管理员在系统中管理系统用户，包括新增用户、编辑用户信息、分配角色（admin 或 viewer）、启用/停用用户、删除用户。

**Why this priority**: 用户管理是权限体系的基础，超级管理员需要能管理系统使用者。

**Independent Test**: 超级管理员能成功新增一个用户（包含用户名、真实姓名、密码、手机号、邮箱、角色），在列表中看到新用户，编辑其信息，并更改角色分配。

**Acceptance Scenarios**:

1. **Given** 当前用户为 admin 角色，**When** 进入用户管理页面并点击新增，填写完整信息提交，**Then** 新用户创建成功，出现在列表中
2. **Given** 用户已在列表中，**When** 点击编辑并修改信息，**Then** 保存后列表和详情显示更新后的值
3. **Given** 用户存在，**When** 点击删除并确认，**Then** 用户从列表中移除（软删除）
4. **Given** 用户状态为启用，**When** 点击停用，**Then** 该用户无法再登录系统
5. **Given** 当前用户为 viewer 角色，**When** 访问用户管理页面，**Then** 仅能看到列表和详情，无新增、编辑、删除按钮

---

### User Story 3 - 整车信息管理（Priority: P2）

管理员维护企业整车车型基础数据，包括新增整车、编辑整车信息、删除整车、查看详情，支持分页查询和按整车编号/名称/品牌条件搜索。

**Why this priority**: 整车数据是系统的核心实体之一，装配关系管理依赖它。

**Independent Test**: 用户能新增一条整车记录（整车编号、名称、型号、品牌、年款、发动机型号、描述），在列表中查看并搜索，编辑和删除该记录。

**Acceptance Scenarios**:

1. **Given** 用户在整车管理页面，**When** 点击新增并填写整车信息提交，**Then** 新整车创建成功，出现在列表末页
2. **Given** 列表中存在整车数据，**When** 在搜索区输入整车编号或名称或品牌并搜索，**Then** 列表仅显示匹配结果
3. **Given** 用户点击搜索后想清空条件，**When** 点击重置按钮，**Then** 搜索条件清空，列表恢复全量显示
4. **Given** 整车数据超过一页容量，**When** 浏览列表，**Then** 分页控件正确显示总页数、每页条数可选
5. **Given** 用户点击查看详情，**Then** 弹窗或新页面展示该整车全部字段信息

---

### User Story 4 - 零部件信息管理（Priority: P2）

管理员维护零部件基础数据，支持新增、编辑、删除、详情查看、分页查询、按零件编号/名称/类别/供应商搜索。当零件库存低于安全库存时，前端标记库存预警标识。

**Why this priority**: 零部件数据是另一核心实体，装配关系管理和库存预警依赖它。

**Independent Test**: 用户能新增一条零部件记录，设置安全库存，当库存数量低于安全库存时列表行显示预警标记，能搜索和编辑该记录。

**Acceptance Scenarios**:

1. **Given** 用户在零部件管理页面，**When** 新增零部件并设置安全库存为 100、库存数量为 80，**Then** 该记录在列表中标记为库存预警状态
2. **Given** 零部件库存充足（库存 ≥ 安全库存），**When** 查看列表，**Then** 该行不显示预警标记
3. **Given** 用户输入零件编号或类别搜索，**When** 点击搜索，**Then** 列表过滤匹配结果
4. **Given** 用户修改零件信息，**When** 编辑保存后，**Then** 更新后的信息在列表中可见
5. **Given** 用户删除某零部件，**When** 确认删除，**Then** 该零部件从列表中移除

---

### User Story 5 - 整车零部件装配关系管理（Priority: P2）

管理员为某整车配置其组成零部件，包括新增装配关系（选择零部件、设置装配数量、装配位置）、编辑装配数量/位置、删除装配关系。支持查看某整车全部 BOM 清单，以及查看某零部件被哪些整车引用。

**Why this priority**: 这是系统的核心业务功能，连接整车和零部件两大实体。

**Independent Test**: 用户选择一辆整车后，能为其添加多个零部件装配关系（每个关联包含零部件、数量、装配位置），查看该整车完整 BOM 清单，清单中显示所有装配的零部件及其数量、位置。

**Acceptance Scenarios**:

1. **Given** 用户已选择一辆整车，**When** 添加装配关系并选择零部件、设置数量和位置，**Then** 装配关系创建成功，在该整车的零部件列表中可见
2. **Given** 某整车已有若干装配关系，**When** 查看该整车 BOM 清单，**Then** 列出全部零部件及其装配数量、位置
3. **Given** 装配关系存在，**When** 编辑装配数量或位置，**Then** 保存后更新值可见
4. **Given** 某零部件被多辆整车引用，**When** 查看该零部件的引用整车列表，**Then** 列出所有引用该零部件的整车
5. **Given** 用户删除装配关系，**When** 确认删除，**Then** 该关联移除，不影响整车和零部件本身数据

---

### User Story 6 - 统计分析（Priority: P3）

首页展示统计卡片和可视化图表，帮助管理者快速掌握系统数据概况。

**Why this priority**: 统计分析提供决策支持，但不影响核心业务功能运行。

**Independent Test**: 首页正确展示四项统计数据卡片，零部件类别柱状图数据与实际分类统计一致，库存预警图表展示预警零件数量趋势，最近新增列表显示最新 10 条记录。

**Acceptance Scenarios**:

1. **Given** 数据库中有 50 辆整车、200 个零部件、5 个用户、3 个预警零件，**When** 访问首页，**Then** 四张卡片分别显示 50、200、5、3
2. **Given** 零部件分布在发动机、底盘、电气、车身等类别，**When** 查看类别统计图，**Then** 柱状图正确显示各类别数量
3. **Given** 用户查看最近新增列表，**Then** 按创建时间倒序展示最新 10 条记录

---

### Edge Cases

- 整车编号（vehicle_code）和零件编号（part_code）在系统中必须唯一，重复提交应提示"编号已存在"
- 删除被装配关系引用的整车或零部件时，需先提示存在关联数据，确认后才能删除（或删除关联后允许删除实体）
- 同一整车不能重复添加同一个零部件的装配关系
- 库存数量为负数时，前端显示为 0 并标记异常
- 分页参数页码为负数或超过总页数时，自动修正到有效范围
- 用户名必须全局唯一，注册时校验
- 连续 5 次登录失败后锁定账户 15 分钟

## Requirements *(mandatory)*

### Functional Requirements

#### 认证模块

- **FR-001**: 系统 MUST 支持用户通过用户名和密码登录，登录成功后返回 JWT Token
- **FR-002**: 系统 MUST 提供获取当前登录用户信息的接口
- **FR-003**: 系统 MUST 支持已登录用户修改个人密码（需验证旧密码）
- **FR-004**: 系统 MUST 提供退出登录功能（前端清除 Token）
- **FR-005**: 系统 MUST 在 Token 过期时拒绝访问受保护资源，并引导用户重新登录

#### 用户管理模块

- **FR-006**: 系统 MUST 支持超级管理员新增用户，包含用户名、真实姓名、密码、手机号、邮箱、角色
- **FR-007**: 系统 MUST 支持超级管理员编辑用户信息（用户名不可修改）
- **FR-008**: 系统 MUST 支持超级管理员删除用户（软删除，不物理清除数据）
- **FR-009**: 系统 MUST 支持超级管理员启用/停用用户，停用后该用户无法登录
- **FR-010**: 系统 MUST 支持超级管理员为用户分配角色（admin 或 viewer）
- **FR-011**: 系统 MUST 支持用户分页查询，每页默认 10 条
- **FR-012**: 系统 MUST 支持按用户名、真实姓名模糊搜索
- **FR-013**: 系统必须内置一个初始超级管理员账户（username: admin）

#### 角色模块

- **FR-014**: 系统 MUST 仅支持两种角色：admin（全部增删改查权限）和 viewer（仅查看权限）
- **FR-015**: 系统 MUST 提供角色列表查询接口

#### 整车管理模块

- **FR-016**: 系统 MUST 支持 admin 角色新增整车信息，包含整车编号、名称、型号、品牌、年款、发动机型号、描述
- **FR-017**: 系统 MUST 支持 admin 角色编辑整车信息
- **FR-018**: 系统 MUST 支持 admin 角色删除整车信息
- **FR-019**: 系统 MUST 支持所有角色查看整车详情
- **FR-020**: 系统 MUST 支持整车分页查询，支持按整车编号、名称、品牌条件搜索
- **FR-021**: 系统 MUST 支持重置搜索条件
- **FR-022**: 整车编号（vehicle_code）在系统中必须唯一

#### 零部件管理模块

- **FR-023**: 系统 MUST 支持 admin 角色新增零部件信息，包含零件编号、名称、类别、规格型号、材质、供应商、单位、单价、库存数量、安全库存、描述
- **FR-024**: 系统 MUST 支持 admin 角色编辑零部件信息
- **FR-025**: 系统 MUST 支持 admin 角色删除零部件信息
- **FR-026**: 系统 MUST 支持所有角色查看零部件详情
- **FR-027**: 系统 MUST 支持零部件分页查询，支持按零件编号、名称、类别、供应商搜索
- **FR-028**: 系统 MUST 在列表中对库存数量低于安全库存的零部件进行可视化预警标记
- **FR-029**: 零件编号（part_code）在系统中必须唯一

#### 装配关系管理模块

- **FR-030**: 系统 MUST 支持 admin 角色为某整车添加零部件装配关系，包含零部件选择、装配数量、装配位置
- **FR-031**: 系统 MUST 支持 admin 角色编辑装配关系的数量和位置
- **FR-032**: 系统 MUST 支持 admin 角色删除装配关系
- **FR-033**: 系统 MUST 支持查看某整车的全部零部件 BOM 清单（含装配数量、位置）
- **FR-034**: 系统 MUST 支持查看某零部件被哪些整车引用
- **FR-035**: 同一整车和零部件组合不能重复创建装配关系

#### 首页统计模块

- **FR-036**: 系统 MUST 在首页展示四项统计卡片：整车总数、零部件总数、用户总数、库存预警零部件数
- **FR-037**: 系统 MUST 在首页展示零部件类别统计柱状图
- **FR-038**: 系统 MUST 在首页展示库存预警统计图
- **FR-039**: 系统 MUST 在首页展示最近新增整车列表（最新 10 条）
- **FR-040**: 系统 MUST 在首页展示最近新增零部件列表（最新 10 条）

### Key Entities

#### SysUser（系统用户）
- **id**: 主键，自增
- **username**: 用户名，唯一，不可为空
- **real_name**: 真实姓名
- **password**: 密码（bcrypt 加密存储）
- **phone**: 手机号
- **email**: 邮箱
- **status**: 状态（1=启用，0=停用）
- **create_time**: 创建时间
- **update_time**: 更新时间

#### SysRole（系统角色）
- **id**: 主键，自增
- **role_name**: 角色名称（admin / viewer）
- **role_desc**: 角色描述
- **create_time**: 创建时间

#### SysUserRole（用户角色关联）
- **id**: 主键，自增
- **user_id**: 用户 ID（外键引用 SysUser）
- **role_id**: 角色 ID（外键引用 SysRole）

#### VehicleInfo（整车信息）
- **id**: 主键，自增
- **vehicle_code**: 整车编号，唯一
- **vehicle_name**: 整车名称
- **vehicle_model**: 整车型号
- **brand**: 品牌
- **year_model**: 年款
- **engine_model**: 发动机型号
- **description**: 描述
- **create_time**: 创建时间
- **update_time**: 更新时间

#### PartInfo（零部件信息）
- **id**: 主键，自增
- **part_code**: 零件编号，唯一
- **part_name**: 零件名称
- **category**: 零件类别
- **spec_model**: 规格型号
- **material**: 材质
- **supplier**: 供应商
- **unit**: 单位
- **price**: 单价（DECIMAL）
- **stock_qty**: 库存数量
- **safe_stock**: 安全库存
- **description**: 描述
- **create_time**: 创建时间
- **update_time**: 更新时间

#### VehiclePartRelation（整车零部件装配关系）
- **id**: 主键，自增
- **vehicle_id**: 整车 ID（外键引用 VehicleInfo）
- **part_id**: 零部件 ID（外键引用 PartInfo）
- **quantity**: 装配数量
- **position_name**: 装配位置
- **remark**: 备注
- **create_time**: 创建时间

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户能在 30 秒内完成从打开系统到成功登录的全流程
- **SC-002**: 管理员能在 2 分钟内完成一个用户的新增、编辑、删除操作
- **SC-003**: 列表页加载时间不超过 2 秒（500 条数据以内）
- **SC-004**: 搜索响应时间不超过 1 秒
- **SC-005**: 库存预警准确率 100%（所有库存低于安全库存的零件均被标记，无误报）
- **SC-006**: 系统支持 50 个用户同时在线操作不出现功能异常
- **SC-007**: 整车 BOM 清单查询完整率 100%（返回该整车所有装配的零部件）
- **SC-008**: 首页统计卡片数据与数据库实际记录 100% 一致

## Assumptions

- 目标用户为企业内部员工，使用环境为办公室桌面浏览器（Chrome 100+、Edge 100+）
- 移动端支持不在 v1 范围内
- 数据库部署在同一内网环境，网络延迟可忽略
- 初始超级管理员账户（admin）由系统初始化脚本自动创建，默认密码首次登录需修改
- 用户密码最小长度 6 位，无其他复杂度要求
- 软删除机制使用 is_deleted 标志位实现，列表默认不显示已删除记录
- 系统不涉及多租户、国际化、审计日志等企业级扩展功能
- 文件上传（如零件图片、文档）不在当前版本范围内
- 数据量预估：整车不超过 500 条，零部件不超过 5000 条，装配关系不超过 20000 条
- 本地开发环境：MySQL 8.x 已通过 Docker 本地启动，用户名 root，密码 123456，数据库名 vehicle_parts。初始建表直接执行 tech-spec.md 中的 SQL 语句预建到数据库中
- 后续数据库变更使用 Alembic 迁移文件管理（alembic upgrade head），初始角色（admin/viewer）和超级管理员账户通过 seed 脚本插入
